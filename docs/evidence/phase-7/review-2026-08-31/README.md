## Defect and correction

With the previous polling code, every two-second check incremented the request generation. If every reply took 2.5 seconds, each arrived after another check had invalidated it. Management stayed in **Checking WebMCP availability…** indefinitely despite successful server replies.

`tests/webmcp-control.test.tsx` reproduces this at the management UI boundary using a real disabled setting and a delayed transport reply. The original code failed the new test; its other five control tests passed (`red-slow-poll.log`). The correction coalesces reads while a request is pending and clears that pending token only for its matching request. Save/unmount invalidation still prevents obsolete responses from replacing newer confirmed state. All six control tests pass (`green-slow-poll.log`). A new desktop/mobile production case also delays real server-function replies by 2.5 seconds and verifies confirmed disabled state, an actionable switch, and no model context.

The correction is confined to `src/availability/availability.tsx`, the two control-test files, and Phase 7 documentation/evidence. Other Phase 7 implementation remains preserved. No further concrete code blocker was found in the import gate, separate settings storage, guarded assistant entry, native API preservation, or ordinary manual submission path.
